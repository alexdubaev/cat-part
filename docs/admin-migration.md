# Установка, перенос, обновление и восстановление

Эти команды предназначены только для localhost стенда. Source — canonical checkout CatPart; `local_catpart` читается лишь по whitelist каталога/статей. Чужие config/users/clients/secrets не читаются и не переносятся. Native каталог устанавливается пустым; сотрудники синтетические.

1. `python tools/admin-package.py build --output PATH.zip` и `verify --package PATH.zip`; сохранить SHA256 sidecar, source revision/tree digest и upstream lock.
2. Preview: `python tools/admin-package.py install --package PATH.zip --target D:/codex/cat-part/admin-stand --source D:/codex/cat-part/cat-part`. Ничего не меняет. Для разрешённого изолированного применения добавить `--apply`. Target должен быть пустым. Если 8095 занят своим временным стендом, сначала выполнить его verified `admin-dev.py stop`; чужие процессы не трогать.
3. Установщик создаёт только собственную `catpart_admin_[12hex]` схему на 127.0.0.1:3307, минимальные native settings/roles и один catalog clone. Новые config/passwords/captures/uploads/backups остаются private. Core извлекается из проверенного upstream, а app/extension/assets — из пакета.
4. `CATPART_ADMIN_RUNTIME` должен указывать на `TARGET/local-dev/admin-runtime`; PHP CLI `tools/admin-data.php inventory` сохраняет private `migration-report.json`: source/target counts, полный old→new ID map, связи, изображения/отсутствующие пути, маршруты и settings sections. Проверить известный baseline: 7134 товара, 1161 категория, 5 статей. Отсутствующие изображения фиксируются честно, не генерируются из чужих данных.

Обновление: сначала остановить свой стенд для согласованного private backup (`tools/admin-data.php backup`), проверить новый ZIP, затем preview `admin-package.py update --package PATH.zip --target TARGET`, потом `--apply`. Обновление заменяет только перечисленный код, не config/runtime/media/DB; вызывает аддитивные миграции и идемпотентный seed. Не запускать fresh setup как upgrade: он предназначен для первоначального native bootstrap. Самый ранний code rollback сохраняется в `private/code-rollback`; последующие обновления не перезаписывают его. Перед новым release-циклом архивируйте эту папку вручную, сохраняя доступный проверенный rollback.

`admin-package.py rollback --target TARGET` показывает план; `--apply` восстанавливает только прежний код и запускает тот же runtime. База не откатывается: новые заказы и обращения сохраняются. Применять только к совместимым аддитивным версиям. Для необратимой схемы нужен отдельный согласованный план; этот пакет такую миграцию не делает.

Backup содержит закрытые данные/хеши локальных учётных записей и хранится только в `runtime/private/backups`. `tools/admin-data.php restore PRIVATE_BACKUP --apply` создаёт совершенно новую собственную случайную task schema и отказывается восстанавливать поверх существующей. Он не переключает рабочую БД и не удаляет неизвестные записи. Проверить digest/counts/чтение в новой схеме до любого решения о восстановлении. Полный DB rollback поверх живой схемы с новыми заявками запрещён этим workflow.

Shipping integration реально применяет пакет дважды, держит старую корзину с исходными ID и qty2/150, проверяет пользовательские/native настройки, товар/картинку, unknown table/settings sentinel, новые native order/lead, затем code rollback после дополнительных заявок. Backup восстанавливается во вторую own schema с побайтовым digest каждого ряда/таблицы; тест удаляет только созданную им restore schema и точные fixtures. Production migration, hosting deployment и реальная почта **NOT RUN**.
